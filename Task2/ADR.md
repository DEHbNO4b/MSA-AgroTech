### <a name="_qmphm5d6rvi3"></a>**Решение**

Плюсы:

✔ Kafka лучше подходит для большого количества событий, телеметрии, стабильной доставки
✔ Kafka tolerates offline/слабую сеть, поддерживает батчевую репликацию (соответствует требованию задержки до 10 минут)
✔ Сообщения упорядочены, есть ретеншн
✔ Лучше соответствует IoT / Edge-heavy архитектуре

Минусы:

✖ Kafka напрямую из Edge — тяжёлая технология, особенно если Edge работает на ARM/микросервере
✖ Требует значительных ресурсов и администрирования
✖ SMS как единственный канал может быть ограничением (в реальности SMS шлюз должен быть локальным)

Соответствие ТЗ:

Вариант 1 ближе к требованиям, особенно к:

оффлайн работе

высокой производительности видеоаналитики

гарантированной доставке событий

распределённости Edge

Но Kafka напрямую может быть overkill – логичнее использовать локальную очередь + Kafka на центральной стороне.

Вариант 2
Отличительные элементы:

Edge → Central: REST

Edge → Telecom: Email

Telecom → Operator: Email

Плюсы:

✔ REST проще внедрять
✔ REST подходит для MVP
✔ Ниже порог входа и проще дебажить

Минусы:

✖ Никак не решает оффлайн-работу
✖ REST плохо работает при прерывистых каналах → потеря событий
✖ Email как основной канал уведомлений категорически не подходит для критических оповещений
✖ Не покрывает требования real-time (<5 сек)

Соответствие ТЗ:

— Реально несоответствует ключевым функциональным требованиям:

задержка до 5 секунд

оффлайн работа

работа через GSM без интернета

видеоаналитика в реальном времени

надёжная доставка уведомлений
REST слишком слабый протокол для Edge-системы мониторинга животноводства, где критичны гарантии доставки и низкая задержка.
